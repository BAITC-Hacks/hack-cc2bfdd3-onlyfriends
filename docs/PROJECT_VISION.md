# PROJECT VISION

## 1. Назначение проекта

Проект создаётся для решения кейса:

**«Agentic AI для прогнозирования выработки ВЭС»**

Владелец кейса: **Самрук-Қазына**.

Главная цель проекта — построить воспроизводимую Agentic AI-систему, которая автоматически формирует **почасовой прогноз выработки ветроэлектростанции на следующие 24–48 часов**, используя:

* исторические данные работы ВЭС;
* координаты двух предоставленных точек / турбин;
* погодные прогнозы, которые были доступны на момент соответствующего исторического запуска;
* ML-модель прогнозирования выработки.

Система должна воспроизводить ситуацию так, как будто прогноз действительно формировался в прошлом.

Главный принцип проекта:

> Система никогда не должна использовать информацию, которая стала известна позже момента прогнозирования.

Качество решения определяется не только точностью модели, но и доказуемой честностью ретропрогноза, воспроизводимостью полного сценария и соответствием фактической реализации заявленной архитектуре.

# 2. Исходные данные

Участникам предоставляются исторические данные ВЭС за период:

**с марта 2023 года по 31 января 2026 года включительно.**

В исходных данных присутствуют:

* статистическое время;
* средняя скорость ветра, м/с;
* нормализированная активная мощность на стороне линии;
* средняя температура окружающей среды, °C.

Также предоставлены две географические точки.

# 3. Главный пользовательский сценарий

Пользователь должен иметь возможность запустить полный прогнозный цикл.

После запуска система самостоятельно:

1. определяет момент прогнозного запуска;
2. загружает необходимые исторические данные станции;
3. проверяет входные данные;
4. получает погодный прогноз для обеих координат;
5. использует только тот погодный выпуск, который был доступен на рассматриваемый момент времени;
6. подготавливает признаки;
7. запускает модель прогнозирования;
8. формирует почасовой прогноз;
9. анализирует полученный результат;
10. сохраняет происхождение прогноза;
11. сохраняет информацию о модели и использованных данных;
12. возвращает результат или явную причину отказа;
13. при появлении новых допустимых входных данных позволяет повторить расчёт.

Agentic AI отвечает за организацию полного цикла.

ML-модель отвечает непосредственно за прогноз численного значения мощности.

Агент не должен заменять ML-модель свободным LLM-предположением.

---

# 4. Горизонт прогнозирования

Каждый прогнозный запуск должен формировать до:

**48 последовательных почасовых прогнозных значений.**

Рабочий горизонт:

**24–48 часов вперёд.**

Основной формат первой версии:

**48 почасовых значений на один прогнозный запуск**, если необходимые погодные данные доступны на весь горизонт.

Если часть горизонта невозможно корректно построить, система не должна незаметно выдумывать отсутствующие значения.

Система должна явно сообщать об ограничении или отказе.

---

# 5. Историческое воспроизведение прогнозов

Необходимо воспроизвести последовательные прогнозные запуски за тестовый период.

Тестовый период:

**1 февраля 2026 года — 28 февраля 2026 года.**

Первый исторический запуск:

**31 января 2026 года.**

После этого запуск повторяется последовательно для следующих дней тестового периода.

Пример:

```text
31 января 2026
    -> прогноз следующих 24–48 часов

1 февраля 2026
    -> новый прогноз следующих 24–48 часов

2 февраля 2026
    -> новый прогноз следующих 24–48 часов

...

28 февраля 2026
    -> соответствующий прогнозный запуск
```

Для финальной оценки качества используются только целевые часы, относящиеся к февралю 2026 года.

Прогнозы могут перекрываться по времени.

Каждый прогноз должен сохранять идентификатор своего собственного запуска.

---

# 6. Строгое правило исторической честности

Это одно из важнейших требований проекта.

Для исторического запуска в момент `T` разрешается использовать только данные, которые могли быть известны системе к моменту `T`.

Запрещается использовать:

* фактическую будущую погоду вместо исторического прогноза погоды;
* погодный прогноз, опубликованный после момента запуска;
* будущую фактическую выработку;
* признаки, рассчитанные с использованием будущих данных;
* статистики, содержащие информацию из будущего тестового периода;
* модель, обученную с использованием будущих относительно запуска данных, если это нарушает выбранную схему ретропрогноза;
* любые другие формы data leakage.

Для погодных данных необходимо по возможности сохранять:

* источник;
* координату;
* время инициализации прогноза;
* время получения / доступности;
* прогнозируемый timestamp;
* lead time;
* используемые погодные переменные;
* идентификатор или версию погодного выпуска.

Если точное время исторической доступности источника невозможно доказать, используемое предположение должно быть явно зафиксировано.

Нельзя скрывать эту неопределённость.

---

# 7. Погодные данные

Система должна самостоятельно получать погодные данные из открытых источников.

Источник выбирается на основании:

* наличия необходимых погодных параметров;
* исторической доступности прогнозов;
* временного разрешения;
* пространственного разрешения;
* возможности определить или обоснованно восстановить время прогнозного выпуска;
* воспроизводимости получения данных.

Погода должна получаться отдельно или корректно сопоставляться для обеих предоставленных координат.

Использование фактических погодных наблюдений вместо требуемого исторического прогноза для оценки ретропрогноза запрещено.

---

# 8. ML-модель

Модель должна прогнозировать предоставленную целевую величину:

**нормализованную активную мощность на стороне линии**, если анализ исходных файлов не докажет другое значение целевой переменной.

Не следует самостоятельно переводить нормализованную мощность:

* в MW;
* в MWh;
* в денежную стоимость;
* в физическую выработку энергии,

пока неизвестна необходимая база нормализации и соответствующее преобразование не подтверждено данными или документацией.

ML-подход выбирается в процессе разработки на основании фактических данных.

Допускается сравнение нескольких подходов.

Но первая версия должна предпочитать:

* проверяемость;
* устойчивость;
* воспроизводимость;
* отсутствие leakage;
* понятную baseline-модель

сложности ради сложности.

---

# 9. Baseline

Проект обязан иметь простой эталонный прогноз.

Основная модель должна сравниваться с baseline на одинаковом временном разбиении и одинаковых целевых часах.

Baseline нужен для доказательства того, что используемый ML-подход действительно приносит пользу.

Конкретный baseline выбирается после анализа данных.

Нельзя объявлять модель хорошей только на основании абсолютного значения метрики без сравнения и контекста.

---

# 10. Временная валидация

Для временных данных нельзя использовать случайное перемешивание train/test, если оно приводит к попаданию будущего в прошлое.

Обучение, validation и backtesting должны сохранять временную причинность.

Все preprocessing-операции должны соблюдать это же правило.

Например, параметры scaler, encoder или других обучаемых преобразований нельзя обучать на будущих данных относительно соответствующего evaluation-периода.

---

# 11. Результат прогнозного запуска

Каждый успешный прогнозный запуск должен возвращать структурированный результат.

Минимально необходимо хранить:

* `run_id`;
* время прогнозного запуска;
* статус;
* версию модели;
* идентификатор набора входных данных;
* источник погодных данных;
* идентификатор / время погодного выпуска;
* координату или идентификатор точки;
* прогнозируемый timestamp;
* горизонт прогнозирования;
* прогноз нормализованной активной мощности;
* информацию о происхождении результата;
* предупреждения;
* обнаруженные аномалии, если они есть.

Необязательно использовать именно эти названия полей.

Схема определяется в реализации, но перечисленная информация должна быть доступна.

---

# 12. Статусы выполнения

Система не должна изображать успешный прогноз, если расчёт невозможно корректно выполнить.

Должны существовать явные состояния выполнения.

Например:

```text
SUCCESS
PARTIAL
FAILED
```

Или эквивалентные значения, соответствующие архитектуре проекта.

Причина ошибки должна сохраняться структурированно.

Примеры причин:

* отсутствуют исторические данные;
* недостаточно данных для признаков;
* отсутствует подходящий погодный выпуск;
* погодные данные повреждены;
* модель не загружена;
* входные данные не прошли проверку;
* нарушено временное ограничение;
* внешний погодный источник недоступен.

Нельзя автоматически заменять отсутствующие критические данные придуманными значениями только для получения результата.

---

# 13. Повторный расчёт

Система должна поддерживать повтор прогнозного цикла при появлении новых допустимых входных данных.

Повторный запуск создаёт отдельный прогнозный run.

Предыдущий результат не должен незаметно перезаписываться таким образом, чтобы потерялось его происхождение.

Должна сохраняться возможность понять:

* какой прогноз был получен;
* когда он был рассчитан;
* на основании каких данных;
* какой моделью;
* каким погодным выпуском.

---

# 14. Agentic AI

Agentic AI является частью задания и должен существовать фактически, а не только в README.

Agentic-часть самостоятельно организует полный workflow:

```text
получение погодных данных
        ↓
валидация
        ↓
подготовка данных
        ↓
запуск модели
        ↓
формирование 24–48-часового прогноза
        ↓
анализ результата
        ↓
сохранение результата и provenance
        ↓
повтор при обновлении допустимых входных данных
```

Agentic-подход не означает, что каждый этап должен выполняться LLM.

Детерминированные задачи должны выполняться обычным кодом.

LLM / агент следует использовать там, где действительно требуется агентное принятие решения, оркестрация, интерпретация состояния или анализ результата.

Не нужно создавать много агентов только для демонстрации multi-agent архитектуры.

Если один агент-оркестратор решает задачу надёжно, этого достаточно.

# 15. Визуализация

Проект должен иметь демонстрационную визуализацию, отражающую смысл задачи.

Основная идея интерфейса:

## Интерактивный земной шар / карта

На визуализации должны отображаться предоставленные точки ВЭС.

Пользователь должен видеть расположение ВЭС и иметь возможность открыть прогнозную информацию для соответствующей точки.

Визуализация должна использовать реальные результаты прогнозного pipeline, а не отдельные демонстрационные значения.

Цель визуализации — понятно показать результат работы системы судьям и пользователю.

На ней следует отображать информацию, уже существующую в системе и относящуюся к ТЗ, например:

* расположение ВЭС;
* выбранную точку / турбину;
* момент прогнозного запуска;
* прогнозный горизонт;
* почасовой прогноз;
* погодные параметры, используемые прогнозом, если они доступны в pipeline;
* статус запуска;
* модель;
* погодный выпуск;
* предупреждения или аномалии.

Визуализация может включать:

* интерактивный глобус;
* приближение к расположению ВЭС;
* маркеры двух предоставленных координат;
* временную шкалу;
* график почасового прогноза;
* карточку выбранной точки;
* отображение прогнозных погодных условий.

Однако визуализация не должна становиться отдельным продуктом с функциями, отсутствующими в задаче.

## Главное правило визуализации

> Визуализация показывает результат прогнозной системы. Она не определяет бизнес-логику прогнозирования.

ML, валидация, provenance и backtesting должны работать независимо от визуального слоя.

11. дальнейшее улучшение модели и интерфейса.

# 17. Что не входит в текущую задачу

Без отдельного подтверждения не реализовывать:

* торговый оптимизатор электроэнергии;
* автоматическую торговлю;
* управление турбинами;
* управление ВЭС;
* SCADA-функции;
* управление оборудованием;
* цифровой двойник всей энергосистемы;
* прогноз цены электроэнергии;
* финансовую модель;
* перевод нормализованной мощности в MWh без известной базы нормализации;
* мобильное приложение;
* систему пользователей и ролей, если она не нужна для демонстрации;
* сложную микросервисную архитектуру;
* Kubernetes;
* распределённую multi-agent систему;
* blockchain;
* дополнительные AI-функции, не связанные с кейсом.

Не добавлять функцию только потому, что она выглядит технологично или эффектно.

Каждая существенная функция должна быть связана либо с заданием, либо с доказуемым улучшением его реализации.

# 19. Метрики

Метрики выбираются после проверки структуры и смысла целевой переменной.

Необходимо использовать метрики, подходящие для задачи регрессии и предоставленной нормализованной мощности.

В отчёте должны быть указаны:

* используемая метрика;
* её определение;
* период оценки;
* количество оценённых часов;
* правила обработки пропусков;
* результат baseline;
* результат основной модели.

Нельзя выбирать или менять метрику только для того, чтобы результат выглядел лучше.

# 21. Наблюдаемость Agentic workflow

Поскольку частью задания является Agentic AI, работа агента должна быть видна.

Для прогнозного запуска должна быть возможность восстановить основные этапы выполнения.

Например:

```text
run created
weather requested
weather validated
features prepared
model loaded
forecast generated
forecast validated
result analysed
result saved
run completed
```

Логирование не должно раскрывать секреты или API-ключи.

Главное требование:

> По журналу должно быть понятно, что полный цикл действительно выполнила система.

# 22. Критерии успешной первой версии

Первая версия считается успешной, если:

* исторические данные корректно читаются;
* временная зона и временная семантика определены или явно зафиксированы;
* погодные данные для двух координат могут быть получены;
* исторический погодный прогноз сопоставляется с допустимым временем запуска;
* отсутствует доказанный future leakage;
* существует baseline;
* существует обученная модель;
* воспроизводятся исторические ежедневные прогнозные запуски;
* каждый запуск формирует требуемый прогнозный горизонт либо явный статус невозможности;
* февральские целевые часы оцениваются отдельно;
* прогнозы имеют provenance;
* результат можно воспроизвести из репозитория;
* Agentic workflow действительно выполняет заявленный цикл;
* ключевые действия агента видны в журнале;
* визуализация использует реальные результаты pipeline;
* архитектура в документации соответствует реально написанному коду.

# 25. Источник истины для coding-agent

Этот документ определяет продуктовую цель проекта.

При реализации агент должен использовать следующий порядок приоритетов:

1. явные требования текущей задачи пользователя;
2. этот `PROJECT_VISION.md`;
3. фактические данные и контракты существующего проекта;
4. `AGENTS.md`;
5. существующие архитектурные соглашения репозитория.

Если идея отсутствует в требованиях и в этом Vision, агент не должен автоматически считать её частью продукта.

Если существует несколько вариантов реализации, агент должен выбирать самый простой вариант, который:

* соответствует этому Vision;
* выполняет требования кейса;
* не нарушает временную честность;
* остаётся воспроизводимым;
* может быть проверен;
* не создаёт ненужную архитектурную сложность.

Агент не должен самостоятельно расширять продуктовый scope.

## Основной принцип

> Не придумывай другой продукт. Построй именно систему прогнозирования ВЭС, описанную в этом Vision.
