# Безопасность и целостность данных

## Границы доверия

Исторический файл станции и ответы погодного API — внешние данные. Они проходят проверку схемы, единиц, диапазонов, временных меток и происхождения до обучения или прогнозирования. Текст из них не может менять системные правила агента или адреса запросов.

Для вызова погодного источника разрешён фиксированный домен и заданные координаты. Параметры URL кодируются, запрос имеет тайм-аут и предел повторов. Источник, модель и публикация каждого использованного выпуска сохраняются для аудита.

## Секреты и доступ

Если погодный провайдер потребует ключ, он передаётся через переменную окружения или менеджер секретов и не попадает в Git, результаты, трассы и сообщения об ошибках. Исходные файлы организаторов публикуются только при наличии права на распространение; репозиторий должен содержать схему и инструкцию получения данных, а не предполагать, что данные можно выложить публично.

Запись прогноза и обучение модели разделены по функциям. Если позже появится многопользовательский интерфейс, проверка прав на запись реализуется в коде, а не в промпте; сейчас такой интерфейс вне объёма проекта.

## Целостность ретропрогноза

Главная защита от ошибочного результата — запрет данных из будущего. Проверяется не только `initialized_at`, но и момент фактической доступности выпуска. Метрики считаются отдельно от обучения; целевые значения февраля не служат признаками до своего фактического появления. Повторный расчёт создаёт прослеживаемую версию без скрытой замены прежнего результата.
